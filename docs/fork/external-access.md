# Внешний доступ: домен, сертификат, подписка

Как устроена публичная часть после переезда на домен.

## Адреса

| Что | Адрес |
|---|---|
| Подписка (короткая) | `https://sub.denuwa.ru/sub/<slug>` |
| Подписка (явная) | `https://sub.denuwa.ru/sub/<slug>/olcbox` |
| Панель (копия) | `https://<ip>:62594` - самоподписанный, только для админа |
| Панель (боевая) | `https://<ip>:62593` - самоподписанный |

Оба адреса подписки отдают один и тот же `sub.md`: nginx переписывает
короткий путь в `/olcbox`, потому что короткий формат панели («client»)
фильтрует провайдеров по белому списку, и `vkcalls`/`salutejazz` в него не
проходят - лента получается пустой.

## Почему домен, а не IP

`sub.denuwa.ru` - CNAME на туннель Cloudflare (proxied, оранжевое облако).
При смене IP у хостера не меняется ничего: клиенты видят только anycast-адреса
Cloudflare. Адреса на основе IP (`152-234-218-18.sslip.io`) годятся только как
временные.

## Cloudflare Tunnel

Мобильные операторы режут прямые соединения к хостинговым адресам (у одного
из них - по белым спискам, у другого блокируется даже TCP-рукопожатие: SYN
проходит, пакеты с данными дропаются, в conntrack сервера ноль записей).
Поэтому подписка отдаётся через туннель:

```
клиент → Cloudflare (anycast) → cloudflared на VPS → nginx 127.0.0.1:443 → панель
```

- сервис `cloudflared.service` на VPS, протокол **http2** (QUIC в этих сетях
  нестабилен), токен в `/etc/cloudflared/token`;
- маршрут в кабинете Cloudflare: `Published application`, `sub.denuwa.ru`,
  Service URL `https://localhost:443`, `Origin Server Name sub.denuwa.ru`,
  `No TLS Verify`;
- на домашнем сервере коннектор пробовали - не регистрируется: провайдер
  душит туннельный трафик. Тот же токен с VPS сразу дал четыре соединения,
  поэтому коннектор живёт на VPS.

## Два хозяина на порту 443

Внешний 443 отдан VLESS Reality (`xray-shark.service`, донор
`shark.denuwa.ru`), потому что Reality на нестандартном порту сам Xray
считает заметным. nginx с подпиской слушает `127.0.0.1:443` - для туннеля
этого достаточно, снаружи порт ему больше не нужен.

```
152.234.218.18:443  → xray-shark (Reality)
127.0.0.1:443       → nginx (только для cloudflared)
0.0.0.0:8443        → nginx, резервный вход по sslip-имени
```

Связать так можно только потому, что Xray биндится на конкретный публичный
адрес, а nginx - на loopback: два `0.0.0.0:443` ядро не пропустит
(`address already in use`).

Адрес в конфиге Xray не высечен намертво: `xray-shark-listen.sh` в
`ExecStartPre` сверяет его с текущим адресом `ens3` и переписывает конфиг,
поэтому смена IP у хостера не оставляет слушателя на мёртвом адресе.

Бэкапы конфигов, действовавших до переезда, лежат в `/root/` с суффиксом
`.bak-<timestamp>`.

Если Cloudflare начнут резать и там, у него есть альтернативные порты
(`8443`, `2053`, `2083`) на тех же адресах - тогда адрес подписки получает
суффикс порта, а nginx и маршрут остаются прежними.

Сертификат для прямого доступа (если понадобится) выпущен
`acme.sh --standalone --httpport 80`, продление автоматическое; порт 80 держим
свободным, nginx на нём не слушает.

## nginx

`/etc/nginx/conf.d/olcrtc-sub.conf`: два серверных блока.

- `listen 443` для `sub.denuwa.ru`, сертификат `/etc/nginx/ssl/denuwa.*`;
- `listen 8443` для старого `152-234-218-18.sslip.io`, сертификат
  `/etc/nginx/ssl/sslip.*` - оставлен как резервный вход.

Оба проксируют на панель `https://127.0.0.1:62594` с `proxy_ssl_verify off`
(внутри самоподписанный сертификат).

## Диспетчер движков и перезагрузка

`olcrtc-prepare` кладёт метку в `/run/olcrtc-engine/<id>`, а движок под
пользователем `olcrtc` её читает. После перезагрузки systemd создавал каталог
с правами `0750 root:root`, метка становилась нечитаемой, и инстансы
запускались старым бинарником: `unsupported provider: salutejazz`. Поэтому в
скрипте теперь есть `chmod 0755 /run/olcrtc-engine`.

## Внешний сторож

На домашнем сервере (`5.166.240.180`) в пользовательском cron:

```
*/2 * * * * /home/denuwa/bin/vps-watch
```

Скрипт раз в две минуты дёргает подписку и пишет в `~/vps-watch.log` каждую
неудачу с временем (`FAIL http=000`), плюс часовую отметку `ok`. Нужен, чтобы
у провайдера были факты: обрывы входящего трафика повторяются, машина при этом
не перезагружается и нагрузка на ней низкая.

## Проверка

```sh
curl -s -o /dev/null -w '%{http_code} %{ssl_verify_result}\n' https://sub.denuwa.ru/sub/<slug>
systemctl is-active nginx olcrtc-panel-gl
grep -E 'public_ip|public_port' /etc/olcrtc-gl-panel/config.yaml
```

## Версия Xray для Reality

Инбаунд живёт на отдельном бинарнике `/usr/local/bin/xray-shark` (Xray 25.3.6),
а не на том, что в комплекте с x-ui. Причина: сервер Xray 26.9.9 отвечает
sing-box-клиенту `REALITY: processed invalid connection: authentication failed`,
а приложение Ghostlane работает именно на sing-box. Проверено вручную:
26.9.9 - отказ, 25.3.6 и 24.12.31 - соединение проходит, `generate_204` через
туннель отдаёт 204.

Поэтому бинарник обновлять с оглядкой: сначала прогнать тест sing-box-клиентом,
потом менять версию. Юнит - `xray-shark.service`, конфиг -
`/etc/xray-shark/config.json`, бэкапы - `/root/xray-shark.json.bak-*`.

## XHTTP за Cloudflare (текущий канал)

Reality на 443 удалён: РКН заблокировал IP `152.234.218.18` для российских
сетей целиком (из-за рубежа порт был открыт, из РФ - таймаут на всех портах,
включая ping). Проверено восемью внешними точками и двумя российскими ISP.

Вместо него VLESS + XHTTP за Cloudflare-туннелем, IP в ссылке не участвует:

`
inbound   Xray 127.0.0.1:8080, path /vpn, mode packet-up
маршрут   rdr2coop.denuwa.ru -> http://localhost:8080 (Cloudflare Tunnel)
юнит      xray-xhttp.service, бинарник /usr/local/bin/xray-shark (25.3.6)
конфиг    /etc/xray-xhttp/config.json
`

**Режим только `packet-up`.** В `auto` Xray выбирает `stream-up` -
длинный дуплексный HTTP-запрос, который Cloudflare буферизует, и соединение
висит до таймаута. `packet-up` отправляет каждый пакет отдельным POST и
через CDN работает.

Ссылка:

`
vless://<uuid>@rdr2coop.denuwa.ru:443?encryption=none&security=tls
  &sni=rdr2coop.denuwa.ru&fp=chrome&type=xhttp
  &host=rdr2coop.denuwa.ru&path=%2Fvpn&mode=packet-up#rdr2coop
`

## Доступ к серверу без входящих портов

Когда входящий трафик режется, шелл берётся через HTTP-форму за тем же
туннелем:

`
https://cmd.denuwa.ru   (Basic auth)   юнит webcmd.service
http://127.0.0.1:7682   POST c=<команда>
`

`ttyd` (веб-терминал) поставлен, но через Cloudflare его WebSocket рвётся
сразу после подключения - для интерактивной работы не годится, оставлен
как есть на 127.0.0.1:7681.

## Ограничение полосы туннеля

Лимит по IP здесь невозможен: Cloudflare скрывает адреса клиентов, на сервере
все они выглядят как `127.0.0.1`. Поэтому ограничивается вся полоса туннеля.

`cloudflared` держит соединение с edge на порту `7844` - это и есть весь
клиентский трафик. Юнит `tunnel-shape.service`:

`
iptables -t mangle -A POSTROUTING -p tcp --dport 7844 -j MARK --set-mark 30
iptables -t mangle -A POSTROUTING -p udp --dport 7844 -j MARK --set-mark 30
tc class 1:30 htb rate 100mbit ceil 100mbit; filter fw handle 30 -> 1:30
`

Менять скорость: `/usr/local/bin/tunnel-shape.sh 50mbit && systemctl restart tunnel-shape`.
Остальной трафик (VK и Jitsi через операторов) идёт по другим портам и под
лимит не попадает.

Старый ограничитель на `tcp/443` (`egress-shape`) удалён вместе с Reality -
публичного 443 на машине больше нет.

## Сторож против наглого трафика

Cloudflare на сетевом уровне скрывает адреса клиентов (все выглядят как
`127.0.0.1`), поэтому наказать конкретного клиента через `tc` нельзя.
Схема такая:

`
cloudflared -> nginx 127.0.0.1:8080 -> Xray xhttp 127.0.0.1:8082
`

nginx нужен только чтобы видеть `CF-Connecting-IP` и писать его в
`/var/log/nginx/xhttp.log`. `limit_rate`/`limit_conn` для этого потока
не работают: одно скачивание приходит одним ответом на десятки мегабайт,
и лимит nginx к проксируемому потоку не применяется (проверено).

Наказание применяет `xhttp-guard.py` (таймер раз в минуту):

- считает байты по каждому адресу из лога за минуту;
- если кто-то взял больше **400 МБ за минуту** и он не в списке исключений
  (`95.68.226.60` офис, `5.166.240.180` дом) - весь туннель уходит на
  **20 Мбит на час** (`tunnel-shape.sh 20mbit`), затем возвращается 100;
- кто именно виноват - видно в `journalctl -u xhttp-guard` ("SLOW: <ip> pulled N MB").

Порог 400 МБ/мин - это примерно 55 Мбит непрерывно, то есть обычный просмотр
и мессенджеры его не достигают, а Steam-закачка упирается сразу.
